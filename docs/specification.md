# Real Estate Lead Management API Specification

## Purpose and Scope

Build a Python API for managing real-estate leads using FastAPI and Pydantic. Work is limited to:

- **Phase 1: FastAPI Foundations**: app startup, centralized settings, Pydantic schemas, a health endpoint, and automated tests.
- **Phase 2: Production Architecture**: router, service, and repository layers, with lead data held in memory.

Databases, authentication/authorization, AI agents, deployment, external integrations, and features beyond these phases are out of scope.

## Functional Requirements

1. Start the FastAPI application through the project's configured entry point.
2. Read application settings centrally from the environment. Existing settings are app name, debug mode, host, and port.
3. Provide the health endpoint defined below.
4. Support creating, listing, retrieving, updating, and deleting leads using the approved lead contract below.
5. Validate API data with Pydantic. Keep HTTP handling, business rules, and storage operations in their respective layers.
6. Use an in-memory repository. Data is available only to the running process and is lost when that process stops.
7. Test successful requests, invalid requests, duplicates, and missing-resource behavior.

## API Endpoints

`GET /health` is implemented in the current project.

| Method | Path | Behavior | Response |
|---|---|---|---|
| `GET` | `/health` | Report that the API is running. | `200`; `{"status": "ok"}` |

The following lead routes are approved Phase 2 contracts.

| Method | Path | Behavior | Response |
|---|---|---|---|
| `POST` | `/leads/` | Create a lead in memory. | `201`; created lead |
| `GET` | `/leads/` | List leads, optionally filtered by city (case-insensitive). `limit` is 1–100 and defaults to 10. | `200`; collection of leads |
| `GET` | `/leads/{lead_id}` | Retrieve one lead by integer ID. | `200`; lead |
| `PATCH` | `/leads/{lead_id}` | Apply a partial update. Empty updates and invalid values are rejected. | `200`; updated lead |
| `DELETE` | `/leads/{lead_id}` | Delete one lead. | `204`; no response body |

Requests for unknown IDs return `404`. A create request with a duplicate phone returns `409`.

## Lead Model and Validation

| Field | Create | Stored/response representation | Validation |
|---|---|---|---|
| `id` | Not supplied | Integer | Auto-generated by the application |
| `name` | Required | String | Non-empty |
| `phone` | Required | String | Non-empty; duplicate comparison trims surrounding whitespace |
| `city` | Required | String | Non-empty |
| `budget` | Required | Integer in PKR | Must be greater than zero |
| `status` | Optional | String | One of `new`, `contacted`, or `qualified`; defaults to `new` |

Reject unknown fields and invalid request bodies with FastAPI's standard `422` validation response. PATCH accepts only supplied fields, rejects an empty body and explicit null values, and validates supplied values using the same field rules as create. Duplicate phone values after trimming surrounding whitespace return `409`.

## Request, Response, and Validation Rules

- Request and response models use Pydantic.
- A valid integer ID that does not identify a stored lead returns `404`.
- Validation failures, including invalid fields, empty PATCH bodies, and non-positive budgets, return `422`.
- Duplicate phone values, compared after trimming surrounding whitespace, return `409`.
- Listing filters cities case-insensitively when `city` is supplied; the default `limit` is 10, and valid limits are 1 through 100.

## Constraints

- Python `>=3.13`; the current runtime dependency is `fastapi[standard]>=0.143.0`.
- In-memory storage only: no durability and no sharing between multiple processes.
- Preserve a repository boundary so storage can be replaced later without putting storage logic in routers.
- Keep all work within Phase 1 and Phase 2 and within the exclusions listed above.

## Acceptance Criteria

1. The configured application entry point starts the API.
2. `GET /health` returns HTTP `200` and exactly `{"status": "ok"}`.
3. Lead create, list, retrieve, partial update, and delete operations match the endpoint contracts above.
4. Lead validation enforces required fields, positive integer budgets, allowed statuses, non-empty PATCH requests, and the stated `422`/`409`/`404` behaviors.
5. City filtering is case-insensitive; list limits below 1 or above 100 are rejected, and an omitted limit defaults to 10.
6. Each lead operation uses a router-to-service-to-repository flow and stores data in memory only for the process lifetime.
7. Automated tests cover successful operations, invalid requests, duplicate phones, and missing leads.
8. No database, authentication, AI agent, deployment setup, or out-of-scope feature is introduced.
